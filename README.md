# SovaGrid Web

Адаптивная веб-панель для просмотра Ubuntu-серверов, графиков CPU/RAM/диска, подробных метрик, событий, истории команд, журнала действий, состояния сервисов Amnezia VPN и собственных WireGuard-инстансов SovaGrid. Команды запускаются через очередь Hub после подтверждения. Для управления собственным WireGuard Agent обращается к ограниченному локальному root broker через Unix-сокет; обычные команды выполняются от имени непривилегированного пользователя Agent. При отдельном подключении локального брокера Amnezia панель позволяет создавать, повторно получать и отзывать профили AmneziaWG и WireGuard, добавленные SovaGrid. Интерактивный терминал, ограниченный текстовый файловый менеджер и настройка Telegram-бота доступны в веб-панели. Начальный экран также поддерживает вход по SSH на Ubuntu-хост, открывший эту панель.

## Запуск

Это статический сайт без сборки. Библиотека xterm поставляется локально в `vendor/`. Манифест и service worker позволяют установить панель как веб-приложение в поддерживаемом браузере; API и метрики не кэшируются. Для локального просмотра:

```bash
python3 -m http.server 8080
```

Тема интерфейса переключается на экране входа, в верхней панели и в настройках: «Как в системе», светлая или тёмная. На устройстве сохраняется только этот выбор. Системный режим следует изменению темы браузера или WebView без перезагрузки; открытая терминальная сессия при переключении не прерывается, а палитра xterm обновляется сразу.

Откройте `http://127.0.0.1:8080`, чтобы посмотреть интерфейс. Для входа настройте reverse proxy, который отдаёт эту папку и `/api/v1/*` с одного HTTPS-домена: Hub не добавляет CORS-заголовки для другого origin. При таком размещении адрес Hub заполнится автоматически.

При размещении через `sovagrid-blueprint/run.sh` начальная форма позволяет войти по SSH-ключу из системного выбора файлов или по паролю SSH. Отдельный непривилегированный `ssh-gateway` подключается только к SSH на том же Ubuntu-хосте, где установлен Hub. Форма запрещает передачу SSH-данных с внешнего HTTP-адреса; используйте HTTPS или локальный `localhost`/`127.0.0.1` через SSH-туннель. Сначала шлюз получает публичный ключ SSH-хоста без аутентификации; пользователь сверяет показанный SHA-256 отпечаток по доверенному внешнему источнику и подтверждает его. При входе шлюз ещё раз проверяет ключ *в самом SSH-рукопожатии до передачи учётных данных*, затем запускает только фиксированную команду получения одноразового Hub-пропуска. Для этого SSH-пользователь должен быть root либо иметь `sudo -n` для этой команды. Пароль, ключ, парольная фраза и пропуск не сохраняются браузером; локально закрепляется только публичный отпечаток ключа SSH-хоста. В форме можно заранее указать имя или ID **уже добавленного** сервера, например добавленный целевой узел, и открыть раздел команд. После SSH-входа на хост панели она выбирает этот сервер из доступного пользователю списка Hub; терминал и остальные операции выполняются через Hub/Agent с обычной проверкой ролей. При отсутствии сервера в разрешённом списке выбирается первый доступный и показывается сообщение. Выбор уже добавленного сервера после входа по SSH всё ещё открывает его через Hub/Agent. Прямой SSH-терминал к новому хосту доступен администратору после входа в панель через «Добавить сервер». Если шлюз недоступен после обновления, остаётся вход по учётной записи Hub.

В диалоге «Добавить сервер» есть отдельный путь для **другого** SSH-хоста. Неограниченный администратор Hub на том же HTTPS-origin вводит адрес и порт, запрашивает через `POST /api/v1/browser-ssh/target-host-key` публичный ключ и независимо сверяет отпечаток. После явного подтверждения он однократно передаёт пароль SSH или приватный ключ в `POST /api/v1/browser-ssh/target-status`. Шлюз повторно проверяет ключ до аутентификации и запускает только фиксированный читающий скрипт состояния Ubuntu/SovaGrid. Интерфейс показывает грубое состояние `missing`, `managed`, `agent_only`, `conflict`, `unsupported` или `unknown`; сырой вывод и секреты не возвращаются. Ввод SSH удаляется из формы после запроса, а на устройстве закрепляется только публичный отпечаток хоста. При изменении закреплённого ключа требуется новая независимая сверка; при изменении адреса, закрытии диалога или выходе незавершённый результат отбрасывается. Для содержательного статуса нужен root или `sudo -n`; двухфакторный SSH-вход пока не поддерживается. Этот этап не устанавливает Agent и не создаёт запись в Hub. После сверки отпечатка отдельная кнопка открывает прямой SSH-терминал этого хоста без Agent. Существующий вариант «Agent вручную» по-прежнему создаёт запись и выдаёт одноразовый токен для отдельной установки.

Прямой SSH-терминал: откройте Hub на том же HTTPS-адресе (или через loopback SSH-туннель), войдите неограниченным администратором, выберите «Добавить сервер» → «Подключить по SSH», введите адрес и порт, независимо сверьте отпечаток, затем укажите SSH-пользователя и пароль или ключ и нажмите «Открыть SSH-терминал». Root не требуется для обычного терминала; права команд определяет выбранный SSH-пользователь. Вывод и ввод находятся только в памяти вкладки, не записываются в Hub и очищаются при закрытии диалога, выходе или смене раздела. Для телефона есть отдельная строка ввода и кнопки Esc, Tab, Ctrl C, Ctrl D, стрелок и Enter. При временном обрыве чтения вывода можно продолжить его с последнего подтверждённого события; если потерян ответ на ввод, команда автоматически не отправляется повторно. Сеанс ограничен временем жизни, бездействием, объёмом ввода и вывода. При необходимости включите ProxyJump: отдельно сверьте ключ промежуточного хоста, введите его SSH-доступ, затем сверьте ключ целевого сервера именно через этот хост. Для открытия терминала SSH-доступ к промежуточному хосту вводится заново; Agent через этот маршрут пока не устанавливается.

В разделе VPN неограниченный администратор Hub может настроить брокер AmneziaWG 3.1 (`awg2`) или WireGuard через SSH на хосте панели либо на другом Ubuntu-сервере, доступном Hub напрямую или через один проверенный промежуточный SSH-хост. Для другого сервера мастер сначала проверяет SSH-ключ и состояние Agent/Hub, затем может подготовить или обновить код `sovagrid-vpn` из проверенного пакета: отдельные предпросмотр, сравнение ревизий, применение и восстановление временных файлов. Этот шаг не создаёт VPN-контейнер и не включает службу. Для уже работающего совместимого контейнера мастер предлагает `enroll-preview → enroll → install → arm`. Перед каждой записью шлюз повторяет проверку прав администратора и состояния; подключение контейнера использует четыре отпечатка CAS. Введённые пароль, ключ и парольная фраза очищаются после формирования каждого запроса; два публичных SSH-ключа и отпечатка маршрута хранятся только в памяти вкладки до смены маршрута или ухода со страницы. В локальном хранилище остаются лишь подтверждённые отпечатки. Шлюз запускает только фиксированные root/sudo-команды; сырые SSH-ответы, ключи и имена клиентов не возвращаются. Промежуточный SSH-хост поддерживается для подготовки VPN-кода, WireGuard-брокера и создания AmneziaWG. Подключение уже работающего брокера (`enroll-preview → enroll → install → arm`) остаётся прямым SSH-маршрутом. Подробный контракт находится в [протоколе шлюза](gateway/VPN_SETUP_PROTOCOL.md).

На чистом Ubuntu-сервере после подготовки VPN-кода отдельный шаг «Новая AmneziaWG 3.1» позволяет выбрать UDP-порт, приватную сеть `/24` и маршрут. По умолчанию `full` направляет IPv4-трафик клиентов через сервер; IPv6 также направляется в туннель, но без IPv6-выхода на сервере может быть недоступен. Режим `split` ограничен VPN-подсетью сервера. Предпросмотр проверяет Docker, `/dev/net/tun`, наличие контейнера и занятость UDP-порта. Применение требует отдельного подтверждения, повторного SSH-входа и совпадения ревизии состояния. Оно создаёт и запускает контейнер `amnezia-awg2`, включает `awg0` и публикует UDP-порт через Docker. Сетевой экран облачного провайдера может потребовать отдельного правила; внешнюю доступность нужно проверить реальным клиентом. Брокер управления включается только после отдельной проверки совместимого работающего контейнера и последующих шагов `enroll-preview → enroll → install → arm`. При потере ответа мастер сохраняет предупреждение в текущей вкладке, требует новый предпросмотр и предлагает отдельное восстановление; SSH-секреты не сохраняются. Веб-маршруты — `POST /api/v1/browser-ssh/amnezia-provision/{preview,apply,recover}`. Сквозная установка и full-маршрут на реальном Ubuntu-сервере пока не проверены; локальные тесты используют имитацию SSH/CLI.

Для обычного WireGuard на отдельном Agent после подготовки `sovagrid-vpn` есть независимый шаг «Обычный WireGuard: локальный брокер». Он показывает состояние установки, недостающие пакеты и таймера инвентаризации. Установка требует отдельного подтверждения и повторного ввода SSH-пароля или ключа; сервер заново сверяет две ревизии. При прерванной операции мастер предлагает проверку и отдельное восстановление. Действие устанавливает root-брокер и включает его сокет и мониторинг, но не создаёт и не включает VPN-интерфейс или клиентские профили. При потере ответа мастер не повторяет запись автоматически. Публичные маршруты — `POST /api/v1/browser-ssh/wg-control/{preview,apply,recover}`; протокол описан в [инструкции](gateway/VPN_SETUP_PROTOCOL.md).

Connect может открыть панель через SSH без повторного ввода пароля Hub. В адресе вкладки он передаёт только порт временного локального посредника (`#sg-bootstrap=<port>`); скрипт сразу удаляет этот фрагмент из истории, забирает одноразовый пропуск только с `127.0.0.1` при локальном origin панели и отправляет его в теле `POST /api/v1/session/ssh-grant`. Нативные WebView могут вместо этого передать пропуск напрямую в JS-контекст через `globalThis.sovagridRedeemNativeSSHGrant(grant)` после своего SSH-входа. Метод принимает только панель на `http://127.0.0.1` и строгий формат пропуска, возвращает `Promise<boolean>`. Пропуск и выданный сеанс не сохраняются в браузере. Если посредник недоступен, пропуск истёк или Hub ещё не поддерживает этот вход, остаётся обычная форма локального пользователя Hub.

При первом входе в Hub без серверов панель открывает раздел «Начало работы». Он показывает связь Hub, количество подключённых Ubuntu-серверов, доступность метрик, разрешение команд в Hub и состояние Telegram из существующих API. Кнопки ведут к настройкам порогов, Telegram, командам, файлам и VPN. Проверка команд в этом разделе относится только к Hub: локальные разрешения Agent и установка дополнительных компонентов проверяются в соответствующих разделах. Вариант «Agent через SSH» в диалоге добавления сервера позволяет после проверки ключа и состояния удалённого Ubuntu-хоста подготовить установку, отдельно подтвердить применение, восстановить прерванную операцию или очистить подготовку. Вариант «Agent вручную» остаётся доступен: ID и одноразовый токен выдаются при создании записи и не сохраняются в браузере. Сквозная проверка применения веб-мастера на чистом Ubuntu-хосте ещё не завершена.

Администратор всего Hub может настроить публичный HTTPS-адрес в «Настройках → Доступ с телефона по HTTPS». Форма показывает текущий IP/домен, путь панели и правило для `/`. Для нового размещения путь по умолчанию `/sovagrid/monitoring/`, а публичный корень `untouched` не открывает панель на `/`: на выделенном HTTPS-адресе корень и неизвестные пути отвечают 404. Существующее правило, например `panel` на ранее настроенном сервере, сохраняется при редактировании. До изменения браузер запрашивает отдельный read-only предпросмотр, затем показывает подтверждение. Применение передаёт точные настройки, оба хеша compare-and-swap и UUID запроса. Только публичная конфигурация и UUID сохраняются на устройстве для восстановления после разрыва; пароль и bearer-токен остаются в памяти вкладки. После ответа или сверки статуса браузер переходит на новый путь без данных входа в URL; потребуется повторный вход. Если ответ потерян, кнопка проверки читает статус Hub, а повтор использует тот же UUID. При смене IP/домена старый origin может перестать отвечать: откройте предложенный HTTPS-адрес и войдите снова. Staging-сертификат не считается доверенным, поэтому автоматический переход на новый origin не выполняется.

Для другого сервера за NAT в соседней секции «Путь панели через SSH» можно задать тот же путь и правило для `/` без публичного IP, домена или сертификата. Форму можно изменить с локального HTTP-адреса своего SSH-туннеля; на публичном HTTPS она только показывает состояние. Локальное `untouched` означает «оставить `/` как сейчас»: существующий базовый Web обычно продолжит открывать на корне панель. Публичное `untouched` означает ответ 404 для `/` и неизвестных путей на выделенном HTTPS-адресе. `GET /api/v1/local-web`, `POST /preview`, `POST /apply` работают через отдельный root broker с CAS и UUID. При потере ответа браузер читает статус и повторяет только прежний UUID. Перед переходом проверяется `GET /api/v1/panel-location`: временный 503 означает «ещё не готово» и **не** заменяется стандартным путём; только 404 старого Hub разрешает fallback на `/sovagrid/monitoring/`. Токен не передаётся в discovery и не добавляется к адресу перехода. Публичный HTTPS и отдельная локальная настройка взаимоисключаются. Для перехода к HTTPS сначала подтвердите «Отключить локальную настройку»: `POST /api/v1/local-web/disable` с CAS и UUID снимает специальный маршрут, оставляет прежний путь `/sovagrid/monitoring/` для SSH-туннеля и сохраняет выбранные path/root как черновик публичной формы на этом устройстве. После этого повторите публичный предпросмотр с новыми хешами.

## Приложение с сайта

На экране входа и в верхней панели есть кнопка «Сделать приложением». Она доступна всем ролям, в светлой и тёмной теме. Панель показывает адрес, который откроется с новой иконки, и подходящую устройству инструкцию. В браузере, предоставившем `beforeinstallprompt`, отдельное нажатие «Установить» вызывает настоящий диалог браузера. Каждый такой запрос используется один раз; отмена или ошибка не выдаётся за успешную установку. Статус добавления появляется только после `appinstalled` или при запуске в standalone-режиме. В обычной вкладке сайт не пытается угадать, установлена ли уже другая его копия.

На iPhone/iPad кнопка показывает шаги Safari: меню страницы → «Поделиться» → «На экран Домой» → «Открыть как веб-приложение», если этот переключатель доступен → «Добавить». На Mac Safari используется «Поделиться → Добавить в Dock»; в остальных браузерах показан запасной путь через меню. Сайт не может сам подтвердить системную установку. Инструкции сверены с [руководством Apple для iPhone](https://support.apple.com/ru-ru/guide/iphone/iphea86e5236/ios), [Safari на Mac](https://support.apple.com/guide/safari/add-to-dock-ibrw9e991864/mac) и [документацией браузерного запроса установки](https://developer.mozilla.org/en-US/docs/Web/API/BeforeInstallPromptEvent/prompt).

Для защищённого веб-приложения нужен HTTPS или доверенный локальный адрес. Администратор может опубликовать панель на `/sovagrid/monitoring/` или другом настроенном пути. Манифест новой PWA задаёт запуск с постоянного адреса `/sovagrid/monitoring/` на том же origin и порту; этот alias остаётся доступен при смене выбранного пути панели. Если на iPhone или iPad панель открыта с другого пути, кнопка установки предлагает сначала перейти по постоянному адресу и уже оттуда добавить её на экран. При публичном правиле `untouched` корень `/` остаётся 404. Смена IP или домена меняет origin и требует нового ярлыка. Ярлык, созданный до этого исправления с произвольного пути, может потребовать повторного добавления, если тот путь уже снят. PWA не переносит SSH-туннель с компьютера на телефон и сама не создаёт SSH-соединение. На телефоне нужен доступный ему HTTPS-адрес панели либо уже работающий на телефоне туннель. Доступные функции и роли остаются такими же, как на сайте; для свежих данных нужна связь с Hub. После запуска с новой иконки может потребоваться повторный вход.

Манифест сохраняет прежний `id` `/` для уже добавленной PWA; `start_url` указывает на постоянный alias, а manifest `scope` `/` охватывает оба маршрута панели. Этот scope задаёт границы окна приложения и не публикует панель на HTTP-корне. PNG-иконки 192/512, отдельные maskable-иконки с непрозрачным фоном и Apple touch icon 180 доступны по постоянному alias. PNG локально растрированы из собственных `icons/sovagrid.svg` и `icons/sovagrid-maskable.svg` с помощью Sharp; генерация картинок через ИИ не использовалась. Service worker зарегистрирован только на `/sovagrid/monitoring/` и держит отдельный кэш для него. При переносе панели с корня прежний SovaGrid worker удаляется после активации нового. Worker хранит только явный список публичных ресурсов оболочки, запрашивает их без cookies и очищает лишь устаревшие кэши своей области. API, Authorization-запросы, неизвестные URL-параметры и профили в Cache API не попадают; ответы `no-store`/`private` не добавляются при обновлении. Пароли, метрики, команды и сеансы для офлайн-доступа не сохраняются.

## Контракт API

- `POST /api/v1/session` с `{ "username": "...", "password": "..." }` возвращает `{ "token": "...", "expires_at": ... }`.
- `DELETE /api/v1/session` отзывает текущий токен.
- Раздел «Настройки» позволяет менять пороги оповещений CPU, памяти, диска, время без связи и задержку тревоги от 0 до 1440 минут прямо в панели. При задержке больше нуля краткие всплески не становятся инцидентами; для нагрузки и служб требуется новое подтверждающее измерение, а отсутствие связи проверяется автоматически. Поля показывают единицы и допустимый диапазон, а Hub применяет сохранённые значения без перезапуска. Если открыта ещё одна вкладка и правила в ней изменились, панель не перезапишет их молча: покажет предупреждение и предложит загрузить сохранённые значения. Здесь же можно сменить пароль администратора без терминала. Это `POST /api/v1/admin/password` с текущим и новым паролями; пароль не попадает в URL или журнал, после успеха поля очищаются и открывается экран входа. Hub завершает все сеансы, закрывает терминалы и отменяет задания, ожидающие отправки агенту. Если есть несохранённые правки файла, панель попросит сначала сохранить или отменить их. Первоначальный пароль в `/etc/sovagrid/admin-password` после смены остаётся старой записью и больше не подходит для входа.

Отдельное правило inode для корневой файловой системы по умолчанию выключено. В «Настройках» администратор с доступом ко всем серверам включает порог использования `(0,100]%` и задержку 30–86400 секунд; наблюдатель и оператор видят действующие значения без кнопки сохранения. Ревизия защищает настройки от перезаписи другой вкладкой; после неопределённого ответа панель требует загрузить сохранённое правило. В обзоре выбранного сервера отсутствие или противоречие счётчиков показывается как «неизвестно», а не как здоровое состояние или восстановление. История закрытого inode-инцидента помечается «Закрыто»: API пока не различает подтверждённое восстановление и административное снятие правила.

В обзоре сервера администратор также может добавить отдельные оповещения о занятом месте или inode для конкретной точки монтирования из свежего отчёта Agent. Для каждого правила задаётся порог 1–100%, для сервера — общая задержка подтверждения 0–86400 секунд. Наблюдатели видят состояние правил. Если список файловых систем неполный, устарел или точка исчезла, панель показывает «Нет достоверных данных»; отсутствие строки не считается восстановлением. После неопределённого ответа на сохранение панель сверяет ревизию и не повторяет изменение вслепую.
- `GET /api/v1/servers` возвращает `{ "servers": [...] }`; элемент содержит `id`, `name`, `online`, `last_seen`, `latest` и `access_role` — действующую роль этого сеанса на данном сервере.
- `POST /api/v1/servers` с `{ "name": "..." }` возвращает `id`, `name`, `created_at` и **однократно** `agent_token`.
- `GET /api/v1/servers/{id}/metrics?limit=60` возвращает `{ "metrics": [...] }`.
- `GET /api/v1/incidents` возвращает `{ "incidents": [...] }`. В истории выбранного сервера видны начало проблемы, время восстановления и её длительность; подтверждённый инцидент остаётся в истории и после восстановления.
- На обзоре выбранного сервера можно начать окно обслуживания на 30 минут, 2 часа или 1 день, указав причину, и досрочно завершить его после подтверждения точного сервера и ID окна. `GET /api/v1/servers/{id}/maintenance` показывает до 100 окон; панель выводит последние восемь. `POST` отправляет только `{ "ends_at": <Unix seconds>, "reason": "..." }`, `DELETE /api/v1/servers/{id}/maintenance/{window_id}` завершает активное окно. Пока окно действует, Telegram-оповещения этого сервера приостановлены; метрики и инциденты остаются видимыми. Сохранившийся к концу окна инцидент вызовет уведомление. Ошибка связи после действия обновляет состояние через GET без слепого повторного POST.
- `POST /api/v1/incidents/{id}/ack` подтверждает событие.
- `POST /api/v1/servers/{id}/commands` включает или выключает очередь команд для сервера в Hub; агент требует отдельного локального разрешения `allow_remote_commands=true`.
- `POST /api/v1/servers/{id}/jobs` с `{ "command": "..." }` и заголовком `Idempotency-Key: <UUID>` ставит команду в очередь. Повтор с тем же ключом, сеансом, сервером и командой возвращает то же задание.
- В разделе «Команды» работает интерактивный PTY-терминал на выбранном Agent от отдельного пользователя `sovagrid-shell`, который не имеет доступа к токену Agent. При установке Agent нужен `--with-terminal`; на сервере нужны локальные флаги `allow_remote_commands=true` и `allow_interactive_terminal=true`, второй по умолчанию выключен. Браузер создаёт сессию через `POST /api/v1/servers/{id}/terminal/sessions` с размером окна и `Idempotency-Key`, читает байтовый вывод через `GET .../{sid}/events?after=N` (long-poll), отправляет ввод через `POST .../{sid}/input` и размер через `POST .../{sid}/resize` с одной монотонной последовательностью `seq`, закрывает сессию через `DELETE .../{sid}`. Можно открыть до четырёх вкладок для разных серверов: у каждой свой экран, курсор вывода, очередь ввода и состояние связи. Ограничение Hub — одна активная терминальная сессия на сервер. После сетевого сбоя кнопка восстановления продолжает с прежнего курсора и повторяет неподтверждённый ввод с теми же байтами и `seq`. Закрытие вкладки ждёт подтверждение Hub; при сетевой ошибке вкладка остаётся для повторного закрытия. Если ответ создания сессии пришёл после закрытия вкладки, браузер отправляет для неё `DELETE`. Выход и уход со страницы закрывают все сессии с ограничением времени жизни на стороне Hub. Сессия привязана к тому же входу администратора; текст PTY не сохраняется в общей истории заданий. Для телефона есть видимое поле для ввода или вставки одной строки с явной отправкой и скрытым режимом для пароля, кнопка вызова клавиатуры и ряд Esc, Tab, Ctrl+C, Ctrl+D, Ctrl+Z, Ctrl+L, стрелок, Home, End, PgUp, PgDn и Enter. Отправленная строка сразу удаляется из поля; несданная строка очищается при переключении вкладок. Содержимое экрана очищается при закрытии или выходе.
- Раздел «Файлы» показывает только разрешённые на Agent каталоги. Текстовый редактор открывает обычные UTF-8 файлы до 8 КБ. «Скачать» принимает двоичные файлы до 32 МБ, а «Загрузить файл» — до 4 МБ; обе операции передают данные частями по 64 КБ. Панель показывает прогресс и просит подтвердить путь, сервер и замену существующего файла. После скачивания она проверяет SHA-256, а Agent перед записью загрузки проверяет размер, SHA-256 и ETag прежней версии. Передачи можно остановить между частями. В Hub требуется разрешение удалённых команд для выбранного сервера; на Agent нужны `allow_remote_commands=true`, отдельный `allow_file_manager=true` и явные `file_roots`. Все операции Agent инициирует исходящим HTTPS. Чтение и запись привязаны к тому же admin-сеансу и ID сервера. Содержимое файлов не хранится в localStorage или SQLite Hub и не записывается в аудит; готовый скачанный файл временно существует как Blob URL в текущей вкладке до сохранения/очистки. Настройка отдельного каталога описана в [Agent README](../sovagrid-agent/README.md#browser-file-manager).
- `GET /api/v1/jobs` возвращает последние задания с состоянием и выводом, а `GET /api/v1/audit` — журнал действий без текста команд.
- Раздел «Логи» предлагает только точные `.service` имена, которые работающий Agent объявил в своём отдельном локальном allowlist. После подтверждения `POST /api/v1/servers/{id}/journal` ставит read-only задание; панель показывает до 100 строк за последние 24 часа и ограниченный 8 КБ результат. После первого успешного чтения можно включить автообновление последних строк на пять минут: не чаще одного нового задания в 30 секунд (не более десяти за один запуск), только пока открыта вкладка и не изменены сервер, служба или права. Каждый ответ заменяет предыдущий снимок. Это периодические снимки, поэтому при ротации журнала или более чем 100 новых строках между ними ранние записи могут не попасть на экран; точный потоковый cursor пока не реализован. Кнопка остановки прекращает новые задания, а неоднозначный ответ сети не повторяется автоматически. Требуются разрешение команд в Hub, `allow_remote_commands=true`, `allow_systemd_journal=true` и список `journal_units` на Agent. Отдельный локальный сервис `sovagrid-journal` читает журналы только для служб из своего root-owned списка. Пустой список Agent скрывает действие. Для действия «Логи» Hub хранит не больше 32 результатов в памяти до пяти минут и выдаёт конкретный текст только сеансу, который его запросил; в SQLite строки этого действия не пишутся. Веб-вкладка также удаляет показанный текст через пять минут и сразу при смене сервера, выходе или уходе из раздела. Выход, смена пароля или перезапуск Hub удаляют серверную копию раньше. Администратор с произвольными командами может обратиться к сокету broker за разрешённой службой, и вывод такой команды сохранится в обычной истории заданий; другие службы broker не откроет.
- Раздел «Службы systemd» запрашивает точное имя `.service`, ставит `status` через `POST /api/v1/servers/{id}/services/actions`, затем читает свежую сводку через `GET /api/v1/servers/{id}/services/control`. После проверки кнопки `start`, `stop`, `restart` доступны около 85 секунд и требуют отдельного подтверждения; Hub независимо требует успешную проверку той же службы в последние 90 секунд. Для служб доступа к хосту, сети, контейнеров, VPN и SovaGrid панель оставляет только проверку состояния; Hub проверяет имя, а Agent с root broker дополнительно проверяют systemd aliases. На Agent нужен отдельно включённый root broker и локальная политика разрешённых служб и действий: даже для других служб успешный `status` не означает право на изменение. Через этот API нельзя передать произвольные параметры `systemctl` или читать журнал. При тайм-ауте либо потере ответа действие могло выполниться: сначала снова проверьте состояние; явный отказ Hub до постановки в очередь показан отдельно. Старый Hub без API покажет предложение обновления.
- Раздел VPN показывает сводку **выбранного сервера с Agent** через `GET /api/v1/servers/{id}/vpn` (роль наблюдателя или выше и доступ к серверу). Ответ содержит `server_id`, `received_at` (UTC, время получения в Hub), `freshness` (`ok`, `stale`, `unavailable`) и `vpn` с тремя независимыми сводками. Устаревание определяется временем получения в Hub, а не часами Agent. Выбор «Хост панели (Hub)» доступен только неограниченному администратору и использует отдельный `GET /api/v1/vpn`; его данные не подменяют сводку выбранного сервера. При `403`, `404` от старого Hub или ошибке запроса панель очищает предыдущие карточки и объясняет состояние. Обе сводки содержат `services` для Docker-контейнеров Amnezia (состояние, health, опубликованные порты), `amnezia_details` для состояния протоколов внутри AWG/WireGuard/Xray (интерфейс или процесс, количество клиентов, активность и агрегированный трафик) и `managed.instances` для собственных WireGuard-инстансов SovaGrid (имя, интерфейс, UDP-порт, подсеть, число клиентов, `active/stopped/error`). У каждой сводки свой `source_status`; ошибка одной не скрывает другие. Снимки обновляются примерно раз в 30 секунд. Ключи, профили, UUID и адреса клиентов API не выдаёт.
- `POST /api/v1/servers/{id}/vpn/actions` с заголовком `Idempotency-Key: <UUID>` ставит в очередь одну из шести операций над собственным WireGuard **на выбранном сервере с Agent**: `create` (`name`, `port`, `subnet`, `endpoint`), `activate` (`name`), `add-client` или `revoke-client` (`name`, `client`), `sealed-export` (`name`, `client`, `public_key`, необязательный `route:"full"`), `remove` (`name`, `confirm_name`, равный имени). Ответ содержит `job`; результат смотрите в списке заданий. Повтор того же запроса с тем же ключом возвращает то же задание. Для выполнения нужны разрешённые команды в Hub и в локальном конфиге Agent, а на выбранном сервере — установленный `sovagrid-vpn-control`. `run.sh --with-wireguard` устанавливает его для исходной конфигурации Hub и Agent на одной машине. Панель требует подтверждения каждой операции и точного ввода имени перед удалением. Полный маршрут VPN предлагается отдельно от split-маршрута и работает только после настройки маршрутизации и NAT на сервере.
- `GET /api/v1/servers/{id}/amnezia/control?target=awg2|wireguard` возвращает состояние выбранной цели opt-in брокера на Agent: `source_status`, `target`, время проверки, признаки подключения и необходимости восстановления, имена клиентов SovaGrid. Кнопка «Проверить управление» создаёт job через `POST /api/v1/servers/{id}/amnezia/actions` с `{action:"status",target}`. Лишь после успешной проверки в течение 90 секунд Hub разрешает `add-profile`, `sealed-export` и `revoke`; при выключенном брокере формы остаются недоступны. Каждая операция использует `Idempotency-Key` и точную схему из [Hub API](../sovagrid-hub/API.md); результат опрашивается через `GET /api/v1/jobs/{id}`. Для добавления профиля указываются имя клиента, публичный адрес сервера и маршрут `split`/`full`. Свободный IPv4-адрес в подсети выбирается автоматически; при необходимости его можно указать вручную в расширенных настройках. В режиме `full` брокер меняет только маршрут выдаваемого профиля; IP forwarding и NAT существующей Amnezia-установки нужно настроить отдельно. Браузер передаёт только временный публичный P-256 ключ, а полученный AWG3 или обычный WireGuard `.conf` расшифровывает в памяти вкладки с проверкой выбранной цели в AAD и предлагает скачать либо сохранить через нативное приложение. Отзыв требует точного ввода имени клиента. Подключение Amnezia к локальному брокеру и восстановление остаются действиями администратора сервера; `run.sh` их не включает автоматически. При старом Hub остаётся совместимый режим AWG2.

Кнопка «Посмотреть настройки сервера» создаёт read-only `settings-preview` для уже проверенного контейнера. Панель показывает порт, подсеть, число клиентов и числовые параметры AWG без ключей и клиентских идентификаторов; цифровые отпечатки доступны в раскрываемых технических подробностях. Снимок не подтверждает доступность UDP-порта извне или работающие параметры AWG. При наличии клиентов изменение настроек потребует отдельной миграции и перевыпуска их профилей.

Для полного набора AWG3-параметров администратор может изменить поля Jc/Jmin/Jmax/S1–S4/H1–H4 в форме и получить расчётный `settings-plan`. Панель передаёт изменённые поля, SHA-256 и поколение показанного снимка; Hub и локальный брокер повторно сверяют их с текущим контейнером. При потере ответа плана кнопка повторяет тот же запрос с тем же ключом, а «Сбросить ввод» возвращает исходные значения. Если клиентов нет и брокер подтвердил работающие селекторы, можно запросить одноразовое подтверждение `settings-intent`. Для этого администратор отдельно включает «Изменение AWG3» в Connect. Панель сверяет цель, обе контрольные суммы, поколение и список полей, показывает точные изменения и сервер в диалоге, а после явного подтверждения отправляет `settings-apply`. Одноразовый код остаётся только в памяти вкладки и удаляется при отмене, смене сервера, выходе и после отправки. При неясном результате применения повтор не предлагается: нужно обновить состояние брокера и снимок настроек. Если клиенты уже есть, план остаётся только для просмотра до реализации миграции и перевыпуска их профилей.
- Раздел «Telegram» позволяет вставить токен BotFather прямо в панели. Поле скрывает ввод по умолчанию; кнопка «Показать» помогает проверить вставленный токен. Hub проверяет токен через Telegram до сохранения, возвращает только маску и состояние, а ввод браузер очищает после отправки. `GET /api/v1/telegram` возвращает статус, публичное имя бота, одобренные роли и ожидающие запросы доступа. `POST /api/v1/telegram/token` с `{token}` сохраняет или заменяет токен, `DELETE` по тому же адресу отключает бота. Если токен задан отдельным файлом в настройках службы, панель показывает состояние, а изменение токена заблокировано.
- Чтобы дать доступ человеку, попросите его открыть ссылку на бота в панели и отправить `/start` или `/connect` в личном чате. В панели появится имя/username, и администратор выбирает роль «Наблюдатель», «Оператор» или «Администратор». Для последней роли панель требует дополнительного подтверждения. `POST /api/v1/telegram/requests/{user_id}/{chat_id}/approve` с `{role}` одобряет запрос, `POST .../reject` отклоняет. Ручной ввод числового ID скрыт в дополнительных настройках и нужен лишь как запасной способ: `POST /api/v1/telegram/bindings` с `{user_id,chat_id,role}`, где `user_id=chat_id` для личного чата. Ручное назначение роли администратора также требует подтверждения точного ID и напоминает о доступе ко всем серверам по умолчанию. Кнопка удаления роли использует `DELETE /api/v1/telegram/bindings/{user_id}/{chat_id}`. Все эти API доступны только администратору Hub. Групповые чаты не поддерживаются.

Административные запросы используют `Authorization: Bearer <token>`. Токен сеанса хранится только в памяти вкладки, а одноразовый токен агента удаляется из интерфейса после закрытия диалога или выхода. Пароль не сохраняется. Адрес Hub сохраняется без учётных данных. Кнопка выхода доступна и в мобильной раскладке.

Если ответ на отправку команды не получен, панель обновляет список заданий и сохраняет ключ операции в открытом подтверждении. Повторное нажатие «Выполнить» с теми же параметрами не создаёт вторую команду. После закрытия подтверждения проверьте список заданий перед новым запуском. Пока Hub и агент не разрешили команды, форма запуска недоступна.

Создание WireGuard-инстанса только готовит конфигурацию; «Запустить» включает интерфейс отдельно. Для добавленного клиента закрытый профиль остаётся на выбранном сервере. При запросе `sealed-export` браузер создаёт новую неэкспортируемую ECDH P-256 пару, посылает только публичный ключ, а закрытый профиль получает в зашифрованном виде через обычный результат задания. Браузер выводит из ECDH общего секрета ключ AES-256-GCM через HKDF-SHA256, расшифровывает файл только в памяти текущей вкладки и предлагает явное скачивание `.conf` или системный Share Sheet на поддерживаемом телефоне. В нативных WebView кнопка скачивания передаёт файл в приложение через `sovagridNativeProfile.postMessage` только по нажатию, когда панель открыта с loopback-адреса. Профиль и закрытый ключ не попадают в DOM, URL, localStorage или журнал заданий. После выхода, закрытия или обновления вкладки запросите новый профиль: старый временный ключ исчезает. HTTPS или доверенный localhost обязательны. Root-only CLI `export-client` остаётся аварийным способом. Сводка выше относится только к хосту Hub и не становится инвентарём выбранного Agent, если это другая машина. Обнаруженные сервисы Amnezia показаны для просмотра; opt-in управление ниже привязано к выбранному Agent и к SovaGrid-клиентам выбранной цели AWG2 или WireGuard.

Контракт нативного сохранения v1: Android объявляет `window.sovagridNativeProfile.postMessage(string)` через `WebViewCompat.addWebMessageListener` с разрешённым origin точного loopback-порта; Apple объявляет `window.webkit.messageHandlers.sovagridNativeProfile.postMessage(string)` через `WKScriptMessageHandler`. Строка содержит JSON `{version:1,filename,data}`, где `filename` строго `<instance>-<client>.conf`, а `data` — канонический base64url без padding с байтами профиля длиной 1–16384. Нативное приложение повторно проверяет origin, основной frame, имя, размер и кодировку перед системным диалогом сохранения; профиль не журналируется.

Метрики: `collected_at` (Unix seconds), `cpu_percent`, `memory_percent`, `disk_percent`, `network_rx_bytes`, `network_tx_bytes`, `load1`, `uptime_seconds`; при наличии также `memory_total_bytes`, `disk_total_bytes` и `details` для swap, файловых систем, интерфейсов, дискового ввода-вывода, load5/load15, процессов и состояний системных служб. Таблица «Топ процессов по памяти» показывает до 10 PID, коротких имён и RSS только из последнего отчёта работающего сервера; при отсутствии данных, ошибке обновления или потере связи показывает явное состояние. Отдельная кнопка «Список процессов» запрашивает у Agent страницу до 32 PID по `POST /api/v1/servers/{id}/processes/snapshot`; фильтр по короткому имени и следующая страница используют PID курсор. Это живой, меняющийся список, ограниченный 4096 строками в панели. Результат доступен только запросившему сеансу через `GET /api/v1/jobs/{id}`, хранится в памяти Hub до пяти минут и в памяти вкладки до выхода или переключения сервера. Аргументы команд, окружение и пути процессов не передаются. RSS включает общие страницы памяти и не равен приватному использованию. Ненадёжные строки вставляются через `textContent`.

Раздел «Контейнеры» показывает отдельные состояния источников Docker и Podman, до 12 контейнеров на источник, UTC-время снимка и его давность. Поля: имя, образ, короткий ID, состояние, здоровье, перезапуски, CPU и RAM при наличии. Отсутствие сокета или доступа видно отдельно, а устаревший снимок не выдаётся за живые данные. Снимок не содержит переменные окружения, метки, пути томов или журналы. Мониторинг включается отдельно на Ubuntu-хосте через управляемый установщик и не даёт Agent/Web доступа к Engine socket.

Администратор выбранного сервера может отдельно запросить последние 20, 50 или 100 строк журнала управляемого контейнера Hub/Web из полного снимка. Сейчас Agent разрешает журналы только контейнеров с Compose-проектом `sovagrid`, службой `hub` или `web` и соответствующим образом `sovagrid-hub:local` или `sovagrid-web:local`; остальные контейнеры остаются только в мониторинге. Web предварительно фильтрует по образу, а Agent проверяет метки и полный ID. `POST /api/v1/servers/{id}/containers/logs` передаёт только Engine, полный ID контейнера и число строк; повтор после потерянного ответа использует тот же ключ операции. `GET /api/v1/jobs/{id}` выдаёт не более 8 КБ временного текста только запросившему сеансу. Содержимое журнала может включать секреты приложения: панель показывает его как обычный текст без интерпретации HTML, не записывает в локальное хранилище или офлайн-кэш и очищает через пять минут, при смене сервера, роли, раздела, выходе или скрытии вкладки. Если Hub или Agent пока не поддерживает эту функцию, появится сообщение об ошибке; для нового запроса нужны разрешённые команды и свежий полный инвентарь контейнеров. Актуальность по часам Hub проверяется на сервере, поскольку часы Agent и телефона могут отличаться. Hub ограничивает частоту таких запросов.

Исходники веб-панели также содержат раздел «Действия с контейнером» для совместимого структурного API Hub/Agent. Он предлагает только точные Docker ID из полного инвентаря, заранее исключает инфраструктуру и требует свежий `status` перед отдельным подтверждением `start`, `stop` или `restart`. Hub и root broker обязаны снова проверить роль, актуальность, точный ID и локальную root-политику; при потере ответа панель запрещает повтор изменения до новой проверки состояния. На установленных узлах эта политика по умолчанию отсутствует, поэтому публикация исходников Web сама по себе не включает действия.

Для сервера с собственным Hub и сохранённым внешним Agent в настройках есть отдельное обновление Agent. В Connect сначала подготовьте проверенный пакет и обновите только локальный Hub, не меняя внешний Agent. Панель принимает SHA-256 этого уже сохранённого пакета, получает read-only `preview` и `preflight`, показывает точные пути изменений и требует отдельного подтверждения. Перед записью root повторно сверяет пакет, исходный Hub и состояние Agent. Браузер создаёт UUID запроса, отправляет `apply` один раз и отслеживает его через `GET /api/v1/external-agent-update/operations/{request_id}`; после потери HTTP-ответа POST не повторяется. Последние операции доступны по метаданным без адресов, ключей и команд. Загрузка пакета с телефона через этот экран пока не реализована; старый Agent без idle-сокета не может пройти безопасное обновление.

## Пользователи и роли

Администратор с доступом ко всем серверам видит в настройках резервные копии Hub. Панель получает только ID, дату, размер базы, признак наличия Telegram-токена и результат проверки целостности. `GET /api/v1/backups` загружает список ID, `GET /api/v1/backups/{id}` проверяет выбранную копию, а подтверждённый `POST /api/v1/backups` с пустым объектом и UUID в `Idempotency-Key` создаёт копию на самом сервере. После потери ответа панель обновляет список; повторить запрос с тем же ключом можно только вручную после нового подтверждения. Копия не скачивается в браузер и не попадает в офлайн-кэш. Для этих маршрутов нужен установленный root broker Hub.

После проверки копии веб-панель предлагает отдельное подтверждение восстановления. `POST /api/v1/backups/restore` передаёт UUID копии и UUID запроса root broker; затем Hub может остановиться, а HTTP-ответ и сеанс могут потеряться. В браузере сохраняется только UUID запроса и выбранной копии, чтобы после нового входа найти журнал через `GET /api/v1/backups/restores` или `GET /api/v1/backups/restores/{request_id}`. Если браузер не подтверждает сохранение UUID на этом устройстве, панель не запускает восстановление или исправление. Повторный POST восстановления после обрыва не отправляется. Для незавершённого запроса, когда Hub доступен, отдельное подтверждение вызывает `POST /api/v1/backups/restores/{request_id}/recover`. Если Hub остался остановлен, веб-API недоступен; тот же запрос проверяется и исправляется через Connect по root SSH. База, токен Telegram и содержимое страховочной копии не передаются браузеру.

В тех же настройках администратор с доступом ко всем серверам видит отдельные копии **всего узла Hub**. `GET /api/v1/host-backups/plan` показывает режим, число служб и контейнеров, которые временно остановятся. После подтверждения браузер сохраняет 32-значный ID запроса на этом устройстве и один раз отправляет его с SHA проверенного исходного пакета в `POST /api/v1/host-backups/operations`. Пока Hub и Web остановлены, ответ может потеряться; после нового входа панель находит запрос по ID через историю или `GET /api/v1/host-backups/operations/{id}`. Повторный запуск при неясном ответе блокируется. Обычные архивы перечисляются и проверяются через маршруты метаданных. Для переносимой копии администратор после проверки пары может скачать архив хоста, точные образы контейнеров и квитанцию по одному файлу через одноразовое разрешение того же Hub. Файлы содержат секреты; браузер скачивает поток напрямую и не загружает многогигабайтный архив в память страницы. Сервер может проверять файл до часа до появления загрузки; браузер не сообщает панели, завершилось ли сохранение. После нажатия «Скачать» панель хранит на этом устройстве только ID операции, тип файла и время начала, блокирует новую загрузку и восстанавливает это состояние после перезагрузки страницы. Администратор подтверждает сохранение файла либо явно отмечает прерванную загрузку для повтора. Если панель открыта с другого origin, для скачивания нужно открыть сам выбранный Hub. Прерванный запрос можно подтвердить для `POST /api/v1/host-backups/operations/{id}/recover`: он возвращает службы без повторного создания архива. Если Hub так и не запустился, проверка и исправление доступны через Connect по root SSH.

В разделе «Настройки → Пользователи панели» администратор создаёт отдельные учётные записи, назначает роль, отключает вход, задаёт новый пароль или удаляет пользователя. Пароль вводится или генерируется в форме; повторно из Hub он не возвращается. Изменение роли, отключение, удаление и смена пароля завершают сеансы только затронутого пользователя и отменяют его ожидающие команды. Последнего действующего администратора отключить или удалить нельзя. При конфликте версий панель требует обновить список.

Наблюдатель видит доступные ему серверы, графики, события и окна обслуживания. Оператор также подтверждает события. Администратор управляет командами, PTY, файлами, журналами и VPN на серверах, где ему выдана роль администратора. Только администратор с доступом ко всем серверам управляет пользователями, Telegram, добавлением серверов и общими порогами мониторинга. Журнал действий администратора с ограниченным доступом фильтруется по его серверам. Проверки прав выполняет Hub; веб-клиент скрывает недоступные действия. Каждый пользователь может сменить собственный пароль в настройках. Доступы SSH настраиваются отдельно.

Кнопка «Доступ к серверам» в списке пользователей и Telegram-привязок открывает список серверов с вариантами «Нет доступа», «Наблюдатель», «Оператор», «Администратор». Можно оставить доступ ко всем серверам; тогда действует общая роль. Выбранная роль на сервере ограничена общей ролью пользователя или Telegram-привязки. Панель читает политику через `GET /api/v1/users/{id}/server-access` или `GET /api/v1/telegram/bindings/{user_id}/{chat_id}/server-access`, а сохраняет через `PATCH` с точной ревизией, режимом и полным списком разрешений. Конфликт `409` требует повторной загрузки и проверки; панель не повторяет изменение автоматически. Изменение прав отменяет ожидающие команды, а для пользователя панели закрывает его терминальные и файловые соединения. Свою учётную запись ограничить нельзя. Веб-клиент читает `GET /api/v1/session/access` и `ServerSummary.access_role`, чтобы показывать доступные действия; Hub повторно проверяет права при каждом запросе. Старый Hub без этих маршрутов продолжает использовать глобальные роли.

Старый Hub с единственным администратором продолжает работать с этой панелью; раздел пользователей попросит обновить сервер. При переходе на новую схему Hub сохраняет данные входа и существующие сеансы прежнего администратора.

### Размещение переносимой копии

Панель проверяет квитанции v1 и v2. Квитанция v2 дополнительно хранит активность, режим автозапуска и хеш каждого управляемого unit-файла; изменения этих полей после проверки сбрасывают разрешение на выгрузку. Поддержка метаданных v2 не добавляет применение полного архива на целевом сервере.

Сохраните все пять файлов. Имена архива и манифеста хоста используют ID архива, который отличается от ID операции: `<archive_id>.tar.gz` и `<archive_id>.manifest.json`. На целевом сервере разместите их в `/var/lib/sovagrid-host-backups/`; файлы `images.tar`, `manifest.json` и `receipt.json` разместите в `/var/lib/sovagrid-host-image-exports/<archive_id>/`. Для каждого файла панель запрашивает отдельное одноразовое разрешение на скачивание. Не меняйте имена файлов при переносе.

## Сетевые проверки

В обзоре выбранного сервера раздел «Сетевые проверки» позволяет добавить конечный URL HTTP/HTTPS, TCP-хост и порт либо DNS-запись A/AAAA с необязательным ожидаемым IP. Все поля, интервал (60–3600 секунд), тайм-аут (1–10 секунд), включение, изменение и удаление настраиваются через формы; отдельная кнопка запрашивает ближайший запуск. До 16 целей на сервер. Настройки доступны администратору, сводка и до 60 последних результатов — всем ролям. Результат включает время, задержку, HTTP-код и фиксированную причину сбоя. Названия и результаты выводятся текстом. Изменение настроек защищено ревизией от перезаписи другой вкладкой.

Проверки выполняет выбранный Agent, поэтому localhost и частная сеть относятся к нему. Целей по умолчанию нет. HTTP делает GET без перенаправлений, не сохраняет тело страницы и считает успехом 2xx. HTTPS проверяет доверие и имя сертификата; администратор может выбрать один доверенный CA в PEM или DER прямо в форме (до 1536 байт в DER) и удалить его кнопкой. Выбранный файл не сохраняется в браузере, а изменение CA сбрасывает прежнюю историю проверки. До истечения 14 дней панель показывает точную дату и предупреждение независимо от оповещений. Для HTTPS администратор может отдельно включить инцидент и Telegram-оповещение об истечении за 1–90 дней; по умолчанию оно выключено. Порог меняется в форме проверки, а активный инцидент показывает остаток срока в днях. TCP проверяет только установление соединения. DNS использует системный резолвер Agent: можно требовать один IP из ответа или просто наличие записи выбранного типа; адреса ответа не сохраняются. Наблюдатели не получают адреса целей из API сводки/истории. Отсутствие Agent показывает ожидание/давность данных и не выдаётся за подтверждённый сбой сайта. Подтверждённый сбой проверки появляется в событиях под её именем; время ожидания берётся из общих настроек мониторинга. Hub отправляет тревогу и восстановление в Telegram по короткому ID проверки, не передавая туда имя или адрес цели. Окно обслуживания временно подавляет оповещения.

Требуются Hub и Agent с протоколом checks v1; для DNS нужны версии с поддержкой типа `dns`. При старом Hub панель предлагает обновление, остальные разделы работают; при старом Agent видна подсказка об отсутствии запросов проверок. Перед включением DNS-цели обновите и Hub, и выбранный Agent: старый Agent этот тип проверки не выполняет.

## Проверка

В `vendor/` находятся официальные локальные сборки `@xterm/xterm` 6.0.0 и `@xterm/addon-fit` 0.11.0 с лицензиями MIT. Терминал загружается с того же хоста панели и не обращается к CDN.

```bash
node --check app.js
node --check browser-ssh.js
node --check files.js
node --check journal.js
node --check container-logs.js
node --check public-web.js
node --check local-web.js
node --check amnezia.js
node --check telegram.js
node --check users.js
node --check access.js
node --check backups.js
node --check host-backups.js
node --test tests/*.test.cjs
cd gateway && npm ci --ignore-scripts && npm test
```

Панель ожидает работающий Hub. Она не содержит демо-данных, которые можно перепутать с метриками настоящего сервера.

GitHub Actions также запускает отдельный тестовый Hub с временной SQLite-базой и браузерные проверки на Chromium и мобильном WebKit. Они проходят настоящие формы создания, изменения, сброса пароля и удаления пользователя, защиту последнего администратора, права наблюдателя/оператора, обе темы и отсутствие горизонтального переполнения.
